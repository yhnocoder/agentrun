运行：命令行与运行时 草稿

前半页写调用方怎么运行 agentrun：命令行选项、一次运行的顺序、启动前检查、doctor 与退出码。后半页每个运行时一节：agentrun 用什么参数启动它、它的原始输出怎么映射到统一事件、什么情况算失败。运行时的参数与行为来自实测，写明了实测的版本；运行时升级后要重新核对。原始输出的完整字段见 claude-code 事件流与 pi 事件流两页字段参考。

命令行界面

核心子命令有 agentrun claude-code、agentrun codex、agentrun pi。三个运行时子命令接受同一组选项。

agentrun claude-code --prompt "给 parse 模块补测试并修复失败"
agentrun pi --model deepseek/deepseek-flash --network custom --allow-host pypi.org --prompt-file task.md
agentrun codex --sandbox off --format jsonl --timeout 600 < task.md
选项含义默认
--cwd DIR会话的工作目录，必须存在。沙箱运行时，它与会话临时目录是 agent 仅有的可写目录当前目录
--prompt TEXT提示词无
--prompt-file FILE从文件读提示词。与 --prompt 同时给出是用法错误无
标准输入前两项都没给时从标准输入读提示词。标准输入是终端时不等待，直接报用法错误；提示词为空也是用法错误
--model ID模型，原样传给运行时。pi 必须写成 服务商/模型，并检查 pi 实际使用的模型是否一致，见pi 一节不传，用运行时自己的默认配置
--effort LEVEL推理强度，传给运行时对应的参数：claude-code 的 --effort、codex 的 model_reasoning_effort、pi 的 --thinking。不检查取值不传
--max-turns N最多轮数，N 为正整数。只有 claude-code 支持，其他运行时给出时是用法错误不限
--timeout SECONDS从运行时启动开始计时，到时终止整个进程组，见进程、信号与超时不限
--sandbox on|relax|off沙箱做不到时怎么办，见沙箱模式。高于环境变量 AGENTRUN_SANDBOXon
--network none|full|custom命令与网页工具能访问哪些主机，见网络none
--allow-host HOST[:PORT]允许访问的主机，可重复，只能与 --network custom 一起给出无
--path DIR放在会话 PATH 最前面的目录，可重复，必须存在无
--env KEY[=VALUE]给会话设置一个环境变量，可重复。只写 KEY 时取调用方环境里的同名变量，见会话环境无
--env-file FILE从文件读取环境变量，可重复，按给出的顺序加载无
--no-subagents不允许 agent 启动 subagent。pi 没有 subagent，给出时不起作用允许
--format rich|text|jsonl标准输出的格式，见事件与输出标准输出是终端时 rich，否则 jsonl
--raw FILE把运行时的原始标准输出逐行写入这个文件，包括无法解析的行不写
--debug在标准错误输出实际执行的命令、会话 PATH、被删除与被设置的环境变量名、凭据写入情况、沙箱检查结果、临时目录的路径与 codex 私有目录的路径（codex home: ）；保留本次运行的临时目录与 codex 私有目录；没有给 --raw 时，原始输出写入临时目录里的 raw.jsonl不开
--dry-run完成命令行解析与启动前检查，把将执行的命令、会话 PATH 与变量名打印到标准输出后以 0 退出。不创建临时目录，不写凭据，不输出事件不开

任何输出都只写变量名，不写变量的值，PATH 除外。提示词不出现在 start 事件的 argv 里；--dry-run 与 --debug 把它写成 <prompt N bytes>。

agentrun 自己写出的文字都用英文：detail、标准错误里的说明、text 与 rich 格式里的固定词、[note] 提示与 doctor 的输出。运行时与模型给出的内容（提示词、模型的文字、运行时的错误信息）原样输出。理由：命令行解析使用现成的库，它的错误信息是英文，全部输出用同一种语言。

启动前检查失败时，写到标准错误的一行是 agentrun: 加 detail。--dry-run 写到标准输出、--debug 写到标准错误，每项一行，格式是 项目名: 值，--debug 的每行前面另加 [debug] 。命令的每个参数按 shell 规则加引号。

$ agentrun pi --sandbox off --env GH_TOKEN --dry-run --prompt "修复测试" command: /usr/local/bin/pi -p --mode json --no-session ... -- '<prompt 12 bytes>' PATH: /usr/local/bin:/usr/bin:/bin set: GH_TOKEN removed: (none)

另外有 agentrun doctor。在 后文 详细描述。

额外传递参数给运行时

-- 之后的所有参数原样传给运行时，用于工具没有提供选项的运行时功能。工具生成的参数在前，-- 之后的参数接在后面。多数运行时遇到同一个选项出现两次时以后一次为准，所以调用方的参数可以覆盖工具的设置。

可以覆盖的设置包括权限与沙箱设置。工具不阻止，只在 start 事件的 argv 里如实记录，这时安全保证由调用方负责。理由：用户需要为没有预料到的用途保留完整的控制。

调用方的参数可能让运行时输出工具不认识的事件，例如给 claude-code 传 --include-partial-messages 后，会多出逐字输出的 stream_event。这类事件不进入统一事件流，只写入 --raw 文件。

一次运行的顺序

启动前检查

以下情形在启动运行时之前报错。标准输出只有一个 end 事件，status 为 rejected，detail 写出原因与修正方法；同一个原因另写一行到标准错误；agentrun 以退出码 2 结束。

  • 用法错误：未知子命令或选项、值不合法、提示词来源冲突或为空、--prompt-file 读取失败、--cwd 或 --path 不存在、--raw 文件无法创建、只写 KEY 的 --env 在调用方环境里找不到、--allow-host 格式不对。
  • --env-file 读取失败或格式错误。
  • 在会话 PATH 里找不到运行时。
  • 凭据写入失败；codex 的登录文件不存在。
  • --sandbox on 时沙箱不可用，或 --network 要求的限制无法执行，见沙箱与网络。
  • 过滤代理启动失败；pi 的服务商不在模型服务主机表里且用 --network none。
  • 会话临时目录创建失败。

命令行解析失败时还不知道 --format 的值，所以先单独扫描一遍参数找 --format，找不到或值不合法时按默认格式输出这个 end。

doctor 检查

agentrun doctor [运行时...] [--model ID] [--sandbox MODE] [--network MODE] [--allow-host HOST]... [--path DIR]... [--env KEY[=VALUE]]... [--env-file FILE]... [--json] [--debug]

按当前环境检查运行时能否使用。不写运行时时检查全部三个，顺序固定为 claude-code、codex、pi。各选项的含义与运行时子命令相同，保证检查的条件与实际运行一致；--path DIR 把目录加到会话 PATH 的前面，可以重复，目录不存在时按用法错误处理。

检查项通过条件
可执行文件（executable）在会话 PATH 里找到，说明里写出路径
登录（login）运行时能用当前环境登录。先按凭据一节写入环境变量给出的凭据。claude-code 运行 claude auth status，读它输出的 JSON 里的 loggedIn；设了 CLAUDE_CODE_OAUTH_TOKEN 时说明写这个变量名，否则写 authMethod。codex 先检查登录文件存在，再用私有 CODEX_HOME 运行 codex login status，退出码 0 为通过。pi 用 --mode json 启动一次，读到 assistant 的 message_start 事件就终止它，不等模型回复；事件里的 provider 与 model 是 pi 实际选中的服务商与模型，给了 --model 时与它比较，否则与 pi 设置里的默认模型比较，不一致时失败。pi 对不存在的模型名只在 stderr 上警告并照用，这个检查把该警告判为失败
沙箱（sandbox）在一个临时目录里，用每个运行时实际使用的沙箱执行一条写文件的命令，确认命令执行了、目录内的文件写出、目录外写不进去。claude-code 的沙箱由它自己在进程内启动，无法单独调用，所以用 agentrun 给 pi 用的包裹代替：两者在 Linux 上都用 bwrap 与 socat，在 macOS 上都用 Seatbelt，检查的是同一组程序能否在当前环境启动。pi 用同一个包裹，并额外在包裹下实际启动一次 pi 与 node。codex 用 codex sandbox 执行同一条命令，文件系统与网络配置同实际运行。检查结束后删除该目录，给了 --debug 时保留并打印路径，保留前删除目录里指向登录文件的链接。--sandbox relax 下沙箱不可用时这一项为 skip，off 时不检查
网络（network）只在 --network full|custom 时检查，且沙箱检查没有运行时为 skip。启动过滤代理，在该运行时实际使用的沙箱里对一个允许的主机发 CONNECT 请求确认能连上，再对一个不允许的主机确认被拒绝。custom 时允许的主机是第一条 --allow-host（通配规则取 www. 加域名），不允许的主机是 doctor-check.invalid:443，要求拒绝原因为 not_allowed。full 时允许的主机是该运行时的模型服务主机（claude-code 为 api.anthropic.com，codex 为 chatgpt.com，pi 为选中服务商的主机），不允许的主机是 169.254.169.254:80，要求拒绝原因为 private_address。codex 的网络由它自己的代理控制：full 时不拦截私有地址，只检查允许的一半；custom 时拒绝来自 codex 代理，说明里不带原因。macOS 上 codex 的 custom 检查失败且主机解析到 198.18.0.0/15 时，说明里指出这是 fake-ip，需要关掉本机代理软件的 fake-ip 模式

每项结果为 ok、fail 或 skip。每个外部命令最多等 30 秒，超时按 fail 记并写明。可执行文件没找到时，登录与网络为 skip；沙箱对 claude-code 与 pi 仍然检查，对 codex 为 fail，因为它的沙箱就是 codex 本身。默认输出每项一行，四列对齐；--json 输出一个数组，每项是 {runtime, check, status, detail}，被信号中断时输出已完成的项。沙箱检查失败时，说明里写明可能的原因与修正方法。

退出码

退出码运行时子命令doctor
0finished所有被检查的项都是 ok 或 skip
1failed有 fail 的检查项
2rejected：启动前失败用法错误、--env-file 读取失败或凭据写入失败
3timeout不出现
130interrupted（SIGINT）被中断
143interrupted（SIGTERM）被终止

调用方只看退出码就能区分「环境未配置好」（2）和「agent 没有完成任务」（1）。退出码为 2 时，调用方不改环境直接重试不会成功。状态的判定顺序见end.status。

claude-code

参数

<claude 的绝对路径> -p --output-format stream-json --verbose
  --input-format stream-json --replay-user-messages
  --permission-mode dontAsk|auto
  --setting-sources ""
  --strict-mcp-config
  --no-session-persistence
  --session-id <新生成的 UUID v4>
  --tools Read,Edit,Write,Glob,Grep,Bash,Task
  --allowedTools <放行列表>
  [--settings <沙箱设置>]
  [--model ID] [--effort LEVEL] [--max-turns N]
  <-- 之后的调用方参数>
  • --setting-sources "" 不加载用户、项目与本地设置，工作目录里的 CLAUDE.md 不进入模型上下文（实测）。因此沙箱设置只来自 --settings。
  • --strict-mcp-config 不加载任何 MCP 服务器。
  • --session-id 每次新生成，与 --no-session-persistence 一起用。理由：在 Claude Code 会话里运行 agentrun 时，claude -p 子进程会继承父会话的 id，把记录写进父会话，只加 --no-session-persistence 不能避免。
  • --tools 限定可用的内置工具，去掉网页工具与技能等。--allowedTools 放行列出的工具，不经权限判断。Bash 不在放行列表里：沙箱打开时由 autoAllowBashIfSandboxed 自动放行，沙箱没有运行时由 auto 模式逐条判断。只用 --tools 而不放行时，auto 模式会拒绝 Write，且结果仍报告成功（实测）。
  • 沙箱打开时权限模式是 dontAsk，放行列表是 Read,Glob,Grep,Task 加上 Edit(//<cwd>/**)、Write(//<cwd>/**)、Edit(//<会话临时目录>/**)、Write(//<会话临时目录>/**)；沙箱没有运行时权限模式是 auto，放行列表是 Read,Edit,Write,Glob,Grep,Task。理由见沙箱与网络。规则里的绝对路径以 // 开头，只写一个 / 时规则不匹配（实测）。
  • 启动 subagent 的工具在参数与 system/init 的工具列表里叫 Task，在输出的 tool_use 里叫 Agent，两个名字都要识别。--no-subagents 从 --tools 与 --allowedTools 里去掉 Task，生效与否看 init 的工具列表里有没有 Task。
  • --network full 时两个列表都加上 WebFetch 与 WebSearch；custom 时 --tools 加 WebFetch，--allowedTools 每个主机加一条 WebFetch(domain:HOST)。
  • 提示词从标准输入传入，不在命令行里：写入一行 JSON {"type":"user","message":{"role":"user","content":"<提示词>"}}，然后关闭标准输入。--replay-user-messages 让 claude-code 把这条消息回显到输出里，agentrun 据此输出 prompt 事件。不加这两个选项时，输出里没有提示词。实测关闭标准输入后进程正常结束（退出码 0）；多行提示词与约 200 KB 的提示词，回显与原文逐字相同；收到 SIGINT 时，回显在中断前已经输出。

沙箱设置（只在沙箱打开时传）：

{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "allowWrite": ["<cwd 的绝对路径>", "<会话临时目录>"]
    },
    "network": {
      "allowedDomains": []
    }
  }
}

allowWrite 与空的 allowedDomains 生效：Bash 能写 allowWrite 列出的目录，不能写 /tmp 的其他位置，不能联网（云端实测）。failIfUnavailable 不能发现沙箱启动失败：PATH 里的 bwrap 启动失败时，claude-code 不报错，每条 Bash 命令以退出码 1 失败，整次运行仍报告成功（云端实测）。所以沙箱能否使用只靠 agentrun 的启动前检查判断，这一项保留作为额外的保护。--network full|custom 时 network 改为 {"allowedDomains":[],"httpProxyPort":<代理端口>,"socksProxyPort":<代理端口>}，两个端口都是过滤代理的 TCP 端口（过滤代理按第一个字节区分 HTTP 与 SOCKS5）；--dry-run 的命令里端口写成 <proxy port>。

输出映射

stream-json 每行一个 JSON 对象。用到的对象与字段：

原始事件用到的字段转成
system，subtype initpermissionMode、model、tools不输出；用于检查 --no-subagents

system，subtype permission_deniedtool_use_id、tool_name、decision_reason把对应的调用标为被拒绝；它出现在对应的 tool_result 之前
user，isReplay 为 truemessage.contentprompt，只取第一条。它在 system/init 之后、第一个 assistant 之前出现，parent_tool_use_id 为 null。之后出现的 isReplay 消息是后台 subagent 交回的结果（内容以 <agent-message 开头），只写入 --raw
user，其他tool_result 块的 tool_use_id、is_error对应的调用结束，输出 tool
system，subtype task_notificationtool_use_id、status、usage.duration_mssubagent_end；status 为 completed 时 finished，其他值 failed
resultis_error、subtype、result、modelUsageend 的 result、失败判定与 usage

  • parent 取所在 assistant 消息的 parent_tool_use_id；它不是任何 subagent_start 的 id 时按 null 处理。
  • subagent：kind 取 input 的 subagent_type，缺省为 general-purpose；model 取 input 的 model；description 取 input 的 description 第一行。subagent 默认在后台运行，启动后立即有一个 status 为 async_launched 的 tool_result，这个结果不输出事件。前台运行的 subagent 没有 task_notification，在收到它的 tool_result 时输出 subagent_end，is_error 为 true 时 failed。subagent 交回结果用的内部工具 SubagentHandback 不输出 tool。
  • usage：claude-code 把一次模型调用拆成多条 assistant 消息（thinking、tool_use、text 各一条），它们的 message.id 相同，每条都带 usage。同一个 id 只输出一个 usage，取最后一条的值，time 取输出时的时间。合并按 parent_tool_use_id 分别进行：主 agent 与每个 subagent 各保存一条待输出的用量，某个 parent 出现新的 message.id 时输出它自己的那条；输出 subagent_end 之前与运行时结束时输出全部待输出的用量。理由：多个 subagent 并行时，它们的 assistant 消息交错出现，只按 id 的先后判断会把一次调用拆成多个 usage。字段：input_tokens、output_tokens、cache_read_input_tokens、cache_creation_input_tokens。model 为 <synthetic> 的消息不输出 usage，它的文字照常输出。
  • 一次运行可能有多个 result：subagent 在后台运行时，主 agent 每收到一个 subagent 的结果就多一轮，每轮一个 result，modelUsage 是到当时为止的累计值。所有用到 result 的地方都取运行时退出前的最后一个。end.usage 由它的 modelUsage 按模型换算。

失败判定

以下任一成立即为 failed，detail 按顺序取第一项的信息：

  1. 最后一个 result 的 is_error 为 true：取它的 result 文字。例如无效模型（同时退出码 1、标准错误有 [claude-code:unrecognized_model]）、无效凭据（退出码 1）。
  2. 退出码非 0：取标准错误的最后 500 个字符。例如未知选项，没有任何事件。
  3. 退出码 0 但没有 result：runtime exited with code N without a result event。

收到 SIGINT 时 claude-code 约 0.4 秒退出，退出码 0，最后的 result 为 is_error: true、subtype error_during_execution；SIGTERM 时退出码 143、没有 result。两种情况都由 agentrun 记为 interrupted。

auto 模式的分类器会拒绝部分命令。实测稳定被拒绝的是读取凭据的命令，例如 cat ~/.ssh/id_rsa；用 curl 把文件外发会触发模型的安全拦截，整次运行以 API Error 失败。

模型检查

--model 必须写成 服务商/模型，可以带 :推理强度 后缀；没有 / 或任一侧为空时是用法错误。理由：pi 对模型名做模糊匹配，能匹配上的未知模型名会被换成别的服务商的模型，退出码仍为 0。例如环境里有 AWS_ 变量时，deepseek/deepseek-v4-flash（1.0.1 已改名为 deepseek-flash）被换成了 Amazon Bedrock 上的模型。

给了 --model 时，agentrun 在第一个 assistant 的 message_start（此时还没有请求模型）比较它的 provider 与 model，区分大小写，不做别名处理。不一致时向进程组发 SIGKILL，判为 failed，detail 为 pi uses <provider>/<model>, which does not match --model <值>。

没给 --model 时不传，pi 用它 settings.json 里的默认模型。设置里的模型不存在、或者没有设置文件时，pi 同样会不提示地改用环境里其他可用的服务商。这种情况由 doctor 的登录检查发现：它报告 pi 实际选中的服务商与模型，与设置不一致时失败。

输出映射

--mode json 每行一个事件，只用以下三种，其余（session、message_update、turn_end、agent_end 等）只写入 --raw。不用 turn_end 与 agent_end，因为它们重复 message_end 的内容，会重复计算用量。

原始事件转成
tool_execution_endtool：id 为 toolCallId，name 为 toolName，parent 为 null，denied 为 false（isError 表示执行出错，不是拒绝）。args 不在这个事件里，从对应的 tool_execution_start 取。同一条消息里的多个调用并行执行，结束顺序可能与开始顺序不同

失败判定

以下任一成立即为 failed，detail 按顺序取第一项的信息：

  1. 模型检查不通过。
  2. 沙箱运行，且标准错误里有包裹命令开头的行（Linux 是 bwrap: ，macOS 是 sandbox-exec: ）、退出码非 0：包裹命令启动失败，detail 为 sandbox failed to start: 加该行去掉这个前缀后的内容。
  3. 退出码非 0：取标准错误的最后 500 个字符。
  4. 最后一条 assistant 消息的 stopReason 为 error 或 aborted：取 errorMessage 的前 500 个字符，没有时写 stopReason: 值。
  5. 退出码 0 但没有 assistant 的 message_end：pi produced no model reply。
