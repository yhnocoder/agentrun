测试与发布

改动 agentrun 的代码后怎么证明它还能用：scripts/test.sh 跑哪些检查，tests/ 里的文件各负责什么，回放样本从哪里来、怎么更新，以及验收脚本在四种环境里怎么运行。单元与集成测试不需要任何运行时与账号，验收脚本需要真实的运行时与登录。

scripts/test.sh

一条命令运行全部检查，任何一步失败就停止并以非 0 退出。提交前在本机运行。

cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
uv run scripts/check_comment.py
shellcheck scripts/accept/accept.sh scripts/accept/lib/*.sh   # 没装 shellcheck 时打印 shellcheck not found, skipped

cargo test 同时运行 src/ 里的单元测试与 tests/ 里的集成测试。需要 bwrap、socat 或 sandbox-exec 的测试在当前环境没有这些程序或它们启动不了时打印 skipped: 开头的一行并通过，所以在没有沙箱的容器里 cargo test 也能全部通过；要覆盖沙箱路径，在装了 bwrap 与 socat 的 Linux 或 macOS 上运行。scripts/check_docs.py 不在 test.sh 里，改动 docs/ 后单独运行，用法见 CLAUDE.md「文档规范」。

tests/ 的分工

每个文件一个主题，文件名就是主题。测试之间可以并行：每个测试用自己的临时目录，端口由系统分配，不读写用户目录与全局配置。

只在进程内调用一个模块、不启动子进程、不改进程级状态的测试写在该模块的测试模块里，过滤代理的测试在 src/network/tests.rs。运行 agentrun、真实沙箱或子进程的测试留在 tests/，每个文件是一个单独的进程。理由：src 里的函数不必为了测试公开，挪动代码时也不用改 tests/；进程级状态（subreaper、信号处理、环境变量、当前目录）在 lib 的单元测试之间共用，只有单独的进程才能互不影响。

文件测试什么怎么测
framework.rs运行框架：事件顺序、subagent 编号与 parent、未结束调用的补发、--raw、退出码非 0 与适配器失败的 detail、会话临时目录的创建与删除、--dry-run 与 --debug 的输出、start 事件记录的沙箱种类FakeAdapter 加一个用 shell 脚本冒充的 claude 可执行文件，在临时目录里的假 PATH 下运行 run::run
session.rs会话环境：子进程环境变量的组装规则、--env 与 --env-file、--debug 与 --dry-run 列出的变量名、AGENTRUN_PI_AUTH 写入登录文件且不出现在输出里、凭据写入失败时在建临时目录之前拒绝与 framework.rs 相同
cli.rs命令行解析与启动前检查：每种用法错误、标准输入是终端且没给 prompt、--format 的预扫描、沙箱不可用时三种 --sandbox 的处理、AGENTRUN_SANDBOX 的来源与优先级、--network 的用法错误、--env 与 --env-file 的错误、--help 与 --version用假的 bwrap 与 socat 脚本模拟缺失、启动失败与挂起；真实 bwrap 或 sandbox-exec 可用时另测通过的情况
claudecode.rs、codex.rs、pi.rs每个适配器：回放样本得到期望的事件流；用假的运行时脚本测 --no-subagents、退出时没有结果事件、私有目录的创建与删除、登录文件检查、AGENTRUN_CODEX_AUTH 写入登录文件并链接进私有目录、模型检查、过滤代理的端口与服务主机assert_replay 回放 tests/fixtures/<运行时>/ 下的样本；其余用临时目录里的假可执行文件
doctor.rsdoctor：运行时去重与顺序、用法错误的退出码、三个运行时的登录检查、沙箱与网络检查的 skip 与 fail、--json、被 SIGINT 中断假的运行时脚本输出固定的登录状态；真实沙箱可用时运行完整的沙箱与网络检查
signals.rs进程组与信号：SIGINT 与 SIGTERM 的转发、5 秒宽限后的 SIGKILL、第二个信号立即 SIGKILL、--timeout、启动前收到信号、沙箱检查期间收到信号、适配器的 launch 期间收到信号而 launch 失败时结果仍是 rejected、被包裹的 pi 直接收到第一个信号、后台进程在退出后被清理harness = false：测试程序自己处理信号，用环境变量 AGENTRUN_TEST_FAKE_AGENTRUN 把自己重新启动成被测的 agentrun 进程，向它发真实的信号。同步靠假运行时写出的文件与事件，每一步最多等 30 秒
concurrency.rs多个运行同时进行：八个运行（claude-code 与 codex 各四个）各用各的会话临时目录，四个 codex 运行还各用各的私有目录（FakeAdapter 以 codex 运行时创建会话临时目录加 -codex 的目录，经 Launch.private_dirs 交给运行框架登记），结束后全部删除（沙箱关闭与打开各一次）；两个 --network custom 的运行只看到自己的 network 事件，沙箱里连不上另一个运行的过滤代理；三个运行中一个被中断、一个正常结束时，只清理自己的进程；十六个运行同时写 AGENTRUN_PI_AUTH（相同的值与不同的值各八个）后登录文件完整、旁注与它一致；十个 --sandbox on --dry-run 同时检查沙箱全部通过，测试输出里打印每个检查的耗时harness = false，与 signals.rs 一样把自己重新启动成被测的 agentrun 进程，每个测试同时启动多个进程。同步靠假运行时写出的文件，不靠固定的等待时间，每一步最多等 30 秒
rich.rsrich 格式：滚动区与面板的内容、标准错误进入滚动区、在伪终端里以 end 行与可见光标结束、NO_COLOR；harness 的 --list 与选项检查harness = false：在伪终端里重新启动自己，读终端的输出
wrap.rsLinux 上 pi 的 bwrap 包裹：只能写工作目录、会话临时目录与登录文件，沙箱里的 TMPDIR，socat 转发，wrapper_failure 识别真实的 bwrap 报错只在 Linux 编译，bwrap 缺失或启动不了时跳过
seatbelt.rsmacOS 上 pi 的 Seatbelt 包裹：写限制、配置文件权限、wrapper_failure只在 macOS 编译

signals.rs、concurrency.rs 与 rich.rs 在 Cargo.toml 里声明 harness = false，理由：cargo 的测试 harness 会安装自己的信号处理，这些主题需要测试程序本身就是收信号、拥有终端、能把自己重新启动成 agentrun 的那个进程。它们用 support/harness.rs 的 run_tests 运行 test_list! 列出的测试函数，输出格式与 cargo 相同。所有测试同时开始，每个测试最多运行 60 秒，超时的测试打印测试名并判为失败。run_tests 支持 --list（输出与 cargo 相同）、--exact、--quiet 与 --ignored（选中的测试为空），接受并忽略 --nocapture、--show-output、--include-ignored 与 --test-threads，其他选项报错并以 101 退出。

写假运行时脚本一律用 support/env.rs 的 write_script，它让 /bin/sh 写文件并设权限，测试进程自己不持有脚本的写描述符，所以 fork 发生在 run::run 里的 framework.rs 与 session.rs 也不会在执行脚本时得到 ETXTBSY。harness = false 的测试程序里，每一次 fork（启动子进程、调用 ps、write_script 启动的 /bin/sh）仍先拿 support/process.rs 的 spawn_lock，理由：open_pty 在 openpty 返回到两个描述符设好 FD_CLOEXEC 之间，另一个线程 fork 出的子进程会继承伪终端的描述符，读 master 要等那个子进程退出才读到结束。spawn_lock 不可重入，support/env.rs 的 write_script 与 Agentrun::spawn、support/mod.rs 的 open_pty 与 sandbox_available、support/process.rs 里调用 ps 的 process_is_gone 自己拿锁，持有锁时不能调用它们。

Agentrun 被丢弃时，如果子进程还没退出，先发 SIGTERM，最多等 TERMINATE_LIMIT（10 s），再发 SIGKILL 并回收。理由：只发 SIGKILL 时 agentrun 来不及结束它启动的假运行时，测试 panic 后会留下进程。

回放样本

tests/fixtures/<运行时>/<场景>.* 每个场景三个文件：

文件内容
<场景>.raw.jsonl运行时的标准输出原文，逐行
<场景>.meta.json{"cwd": "...", "exit_code": N, "stderr": "..."}：记录时的工作目录、运行时的退出码与标准错误。cwd 用于把工具调用里的绝对路径转成相对路径，exit_code 与 stderr 用于失败判定
<场景>.events.jsonl期望的统一事件流，不含 start 与 end 之前的启动过程，含 end

support::replay 读 raw.jsonl，按 meta.json 构造 Invocation 与 Exit，以 dry-run 方式调用适配器的 launch（codex 另给 AGENTRUN_CODEX_AUTH 的内容使登录检查通过），再把每行交给 translate_line，最后调用 conclude 并传入 Launch 记录的包裹方式，得到的事件去掉 time 与 duration_ms 后与 events.jsonl 逐个比较。tests/fixtures/fake/basic.* 没有 meta.json，给 FakeAdapter 用。

样本来源：scripts/probe/probe.sh 在 Cloud Managed 容器、docker 与 macOS 上直接运行三个运行时，每个场景一个目录，记录原始输出、退出码与标准错误；meta.json 里 /tmp/agentrun-probe-<随机>/<场景>-<运行时> 形式的 cwd 就是这些目录。events.jsonl 是写适配器时由当时的适配器生成、逐条核对后保存的。样本记录时的运行时版本见运行页的「运行时版本」。

更新样本的步骤：

  1. 在装有该运行时的环境里录制原始输出。claude-code 与 codex 运行 scripts/probe/probe.sh --runtimes <运行时> --only <场景>，或者直接用 agentrun <运行时> --raw <文件> --format jsonl 运行一次，--raw 文件就是新的 raw.jsonl。pi 只用 agentrun pi --raw <文件> --format jsonl 录制，因为 probe 为 pi 另建状态目录并只写默认服务商与默认模型，agentrun 直接使用用户的状态目录（见pi 使用用户的状态目录），用 probe 录制的样本与 agentrun 实际运行的环境不同。
  2. 把工作目录、退出码与标准错误写进 meta.json。
  3. 运行 cargo test --test <运行时> replay_<场景>，失败输出里的实际事件与期望事件逐条比较，确认差异来自运行时的变化而不是适配器的错误，再把实际事件写进 events.jsonl。

新增或更新样本前检查 raw.jsonl 与 meta.json 里没有令牌、API key 与用户目录的路径，仓库是公开的。

验收脚本

scripts/accept/accept.sh 用真实的运行时与登录把 agentrun 跑一遍，按退出码、事件流与工作目录里的文件判定每个场景，输出一张总表。它是「Validate」步骤的工具，不在 scripts/test.sh 里运行，理由：需要三个运行时的账号，并且要消耗模型调用。

scripts/accept/accept.sh [--agentrun PATH] [--runtimes claude-code,pi,codex] [--sandbox on|relax|off]
                         [--label NAME] [--out DIR] [--only NAME,...] [--parallel N]
                         [--claude-model ID] [--pi-model ID]
选项含义默认
--agentrun PATH被测的 agentrun仓库里的 target/debug/agentrun，不存在时用 PATH 里的 agentrun
--runtimes LIST要跑的运行时，逗号分隔claude-code,pi,codex
--sandbox MODE传给每次运行的 --sandboxon
--label NAME输出目录名的前缀<macos|linux>-sandbox-<mode>
--out DIR输出目录的上级目录./accept-out
--only NAME,...只跑这些场景；sandbox-check 总是运行，因为它决定其他场景是否适用除 concurrent-* 外的全部场景
--parallel Nconcurrent-same 与 concurrent-interrupt 同时启动的运行数3
--claude-model ID、--pi-model IDclaude-code 与 pi 的 --model；codex 不传 --modelsonnet、deepseek/deepseek-flash

场景按下表顺序运行，每个场景对每个运行时各跑一次，不适用的组合记为 skip。

场景检查
sandbox-check用 --sandbox on --dry-run 探明当前环境的沙箱能否运行：退出码 0 为可用，退出码 2 且 detail 以 sandbox is not available: 开头为不可用。沙箱不可用且 --sandbox on 时，依赖沙箱的场景（outside-write、session-tmp、三个 network-*）为 skip；relax 与 off 时再用指定的模式 --dry-run 一次，确认命令里的沙箱种类与预期一致
dry-run、usage-error--dry-run 打印命令并以 0 退出；用法错误只有一个 rejected 的 end，退出码 2
relax-note沙箱不可用时 --sandbox relax 的 text 输出第一行是 [note]；codex 不适用
basic-taskagent 写一个文件并读回，end.status 为 finished，文件内容正确，有 prompt、tool、usage 事件
outside-write让 agent 用 shell 命令写工作目录之外的文件，文件不存在
session-tmp用 --debug 运行，让 agent 把 $TMPDIR 写进文件：它在标准错误 [debug] tempdir: 给出的会话临时目录之下（macOS 上 claude-code 的例外见会话临时目录）；凭据来自环境变量时有 [debug] credentials: 行
network-none让 agent 用 curl 访问 api.github.com，得到的状态码不是 200；pi 另外要求事件流里 api.github.com:443 的 network 事件为 not_allowed，模型服务主机的事件为放行
network-custom--allow-host api.github.com，text 格式：api.github.com 得到 200，example.com 不是 200，输出里有 [main] net denied example.com:443 (not_allowed) 一行；codex 改为检查 --debug 命令行里有 --enable network_proxy
network-fullapi.github.com 得到 200，169.254.169.254 不是 200 且有 private_address 的 network 事件（claude-code 没有事件时也算通过，它的沙箱把私有网段写进了 NO_PROXY）；codex 不经过过滤代理，只检查前一半
webfetch只对 claude-code：--allow-host example.com 下 WebFetch 读 example.com 的 tool 事件 denied 为 false，读 www.iana.org 的为 true
subagents、no-subagents让 agent 用 subagent 写文件：默认有 subagent_start 且 subagent_end 为 finished（codex 没有这两个事件，只检查文件），--no-subagents 下没有 subagent_start（codex 另检查 argv 里有 agents.enabled=false）；pi 不适用
config-isolation工作目录里放写有随机口令的 CLAUDE.md 与 AGENTS.md（codex 另在一个 CODEX_HOME 里放 AGENTS.md），让 agent 不读文件直接回答口令：输出里没有口令为通过；agent 还是用工具读了文件时记为 skip，需要重跑
fail-model、fail-arg、fail-credential不存在的模型、-- 之后传给运行时的未知选项、无效凭据都得到 failed 与退出码 1，detail 非空
interrupt、timeout让 agent 运行一条 120 秒的命令：运行中发 SIGINT 得到 interrupted 与退出码 130，发 SIGTERM 得到 143，都在信号后 8 秒内退出；--timeout 10 得到 timeout 与退出码 3，20 秒内退出
cleanup让 agent 启动一个脱离父进程的后台 node 进程：运行结束后该进程不存在，临时目录下的 agentrun-* 目录与运行前相同
doctor运行两次 agentrun doctor <运行时> --json，第二次加 --network custom --allow-host api.github.com：沙箱项与 sandbox-check 探明的情况相符，没有其他 fail；沙箱运行时第二次的网络项为 ok，否则为 skip

下表的并发场景只在 --only 列出时运行，理由：它们同时调用多次模型，费用与耗时都比其他场景高；cleanup 场景比较 agentrun-* 目录集合的检查也不能与它们同时进行。前四个场景对每个运行时各跑一次，concurrent-mixed 在所有运行时之后跑一次；sandbox-check 判为沙箱不可用的运行时不参加。每个并发运行有自己的记录目录，名字是场景、运行时加序号或所放行的主机，例如 concurrent-same-pi-1；场景本身的 check.txt 与之后补跑的 basic-task 记录在不带序号的 concurrent-same-pi/ 里。

场景做法通过条件
concurrent-same同一个运行时同时启动 --parallel 个 basic-task，各用各的工作目录全部 finished，每个工作目录的 accept.txt 都是 hello
concurrent-same-cwd同一个运行时的两个运行同时用同一个工作目录，分别写 a.txt 与 b.txt两个都 finished，两个文件内容正确
concurrent-network沙箱运行时，两个 --network custom 的运行分别放行 api.github.com 与 example.com，都访问这两个主机每个运行只有自己放行的主机得到 200；每个运行的事件流里，自己放行的主机没有被拒绝的 network 事件，另一个主机没有被放行的事件（codex 只查结果，原因同 network-custom）
concurrent-interrupt同时启动 --parallel 个运行 120 秒命令的运行，都带 --timeout 30；第一个运行在 prompt 事件 8 秒后收到 SIGINT第一个以 130 退出，其余以 3 退出
concurrent-mixed--runtimes 里每个运行时各一个 basic-task，同时启动全部 finished

每个并发场景结束后再检查共享的状态，任何一项不满足都判 fail：跑了 claude-code 时 ~/.claude.json 是合法的 JSON，跑了 pi 或 codex 时用户的登录文件（存在时）是合法的 JSON；用同一个运行时再跑一次 basic-task 并完成，确认登录仍然有效；临时目录下的 agentrun-* 目录与场景开始前相同；工作目录在脚本私有目录之下的进程都已结束（还在的进程写进说明并结束它们）。残留进程按工作目录找，不按命令名找，理由：按 claude 这样的名字匹配会找到机器上与验收无关的进程。

输出目录 <out>/<label>-<时间戳>/：env.txt 记录运行时版本、沙箱程序与每个运行时的 --dry-run 命令；summary.md 每个场景与运行时一行，列为场景、运行时、pass|fail|skip 与说明；每个组合一个 <场景>-<运行时>/ 目录，内有 cmd.txt、stdout.jsonl（text 格式的场景为 stdout.txt）、stderr.txt、exit_code、duration_ms、raw.jsonl 与 check.txt。有任何 fail 时脚本以 1 退出。分享输出目录前先读 stderr.txt，运行时的诊断信息写在那里。

scripts/accept/Dockerfile 基于 ubuntu:24.04，装 Node 22、用 npm 装三个运行时、bubblewrap、socat、curl 与 procps，并写入一份选中 deepseek/deepseek-flash 的 pi settings.json。镜像里不含 agentrun 与凭据：agentrun 由宿主用 rust:1-bookworm 容器交叉构建后挂载，凭据只经环境变量进入，不挂载用户的 HOME。

四种环境里的验收

验收由用户执行，AI 提供步骤与脚本。每种环境里先跑 scripts/test.sh，再跑验收脚本；沙箱打开与关闭各跑一遍，因为两种模式走的是不同的代码路径。

环境谁运行命令说明
Cloud Managed 容器AIscripts/accept/accept.sh --runtimes claude-code,pi，再加 --sandbox off 跑一遍容器里有 claude-code 与 pi 的登录，没有 codex。bwrap 能启动，沙箱路径在这里验证
dockerAI 与用户按 accept.sh --help 里的三条 docker 命令：构建镜像、在 rust:1-bookworm 容器里构建 Linux 版 agentrun、挂载后运行脚本；先 --runtimes claude-code,pi --label docker-on，再 --sandbox off --label docker-off 跑全部三个运行时默认权限的 docker 容器里 bwrap 启动不了，这里验证的是 --sandbox off 与 on 下正确拒绝的路径。凭据经 CLAUDE_CODE_OAUTH_TOKEN、AGENTRUN_PI_AUTH、AGENTRUN_CODEX_AUTH 与 pi 服务商的 key 变量传入
本机 Linux用户cargo build，scripts/accept/accept.sh，scripts/accept/accept.sh --sandbox offUbuntu 23.10 以后要先按沙箱与网络放行 bwrap。三个运行时都用本机的登录
本机 macOS用户同本机 LinuxSeatbelt 路径只能在这里验证。本机开着代理软件的 fake-ip 模式时，codex 的 network-custom 场景会失败，见doctor 检查
