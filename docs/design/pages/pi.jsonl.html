pi 事件流 字段参考

本文是 pi -p --mode json 输出的事件流的字段参考：每种事件何时出现、有哪些字段、字段的类型与含义、典型运行的顺序、错误与退出码、与旧版本的差异。写给要为这条流写解析器的人，不依赖 agentrun 的其他文档。依据是 pi 1.0.1（npm 包 @earendil-works/pi-coding-agent）在 Linux 容器里的实测输出，以及随包安装的 docs/json.md、docs/message-types.md、docs/session-format.md、docs/cli-integration.md 与 CHANGELOG.md。字段表中标出了每一项的来源。

读这条流的三条规则：第一行是 session 头，之后每行一个事件，按 type 分发，不认识的类型跳过；message_end 里的 message 是权威的完整消息，message_update 只用于实时显示；成败看最后一个 assistant 消息的 stopReason，退出码只区分启动失败与被中断，模型调用失败时退出码仍是 0。

怎样产生这条流

pi -p --mode json \
  --no-session --no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files \
  --offline --tools read,bash,edit,write,grep,find,ls \
  -- "提示词"

--mode json 选择逐行 JSON 输出，处理完命令行给出的全部提示词后退出，运行中不接受新的输入。-p（--print）在 --mode json 下可以省略，加上它的效果相同。提示词也可以从标准输入管道传入。标准输出里只有 JSON 行，诊断信息写到标准错误。

以下选项改变流的内容：

选项对流的影响
--model <pattern>、--provider <name>决定 assistant 消息的 provider、model、api 字段。模型名不存在时进程启动失败，见「错误、中断与退出码」
--thinking <level>off、minimal、low、medium、high、xhigh、max。决定 assistant 消息的 thinkingLevel，以及是否出现 thinking 内容块。也可以写成 --model 名字:级别
--tools <list>替换整个工具列表，决定 system 消息的 toolsAdded 与模型能调用的工具名。默认是 read、bash、edit、write
--session-id <id>决定 session 头的 id。不给时 pi 生成一个 UUID v7
--no-session不把会话写到磁盘。流的内容不变，仍然输出 session 头
--no-extensions、--no-skills、--no-prompt-templates、--no-themes、--no-context-files不加载对应的扩展与配置。关闭扩展后不会出现扩展产生的事件（entry_appended、自定义消息角色）；关闭上下文文件与技能后 system 消息的 sections 更短
--offline不检查更新、不刷新模型目录。流的内容不变
--system-prompt、--append-system-prompt改变 system 消息 sections 的内容。未实测

模型 API 的凭据通过环境变量（例如 DEEPSEEK_API_KEY、ANTHROPIC_API_KEY）、pi auth 保存的登录信息或 --api-key 提供。本文样本使用 deepseek provider 的 deepseek-flash 模型，走 openai-completions API；其他 provider 的 api 值、rawStopReason 值与 thinking 块的签名形式会不同。

每行的格式

每行是一个 JSON 对象，以 LF 结尾。文档要求按 LF 切行，去掉行尾可选的 CR，不要把 Unicode 行分隔符（U+2028、U+2029）当作行界，它们可以合法地出现在 JSON 字符串里。每个对象都有 type。除 type 之外没有所有事件共有的字段：事件本身没有 id、时间戳和会话 id，时间戳在 message 对象上（timestamp，Unix 毫秒整数），会话 id 只在第一行的 session 头里。

读取方必须持续消费标准输出。文档说明管道缓冲区满时 pi 会阻塞。

有哪些事件

「来源」一列：「观测」表示在 1.0.1 的样本中出现过；「文档」表示只在 docs/json.md 中有描述；「0.73.1 观测」表示在 0.73.1 的样本中出现过、1.0.1 的样本里没有遇到触发条件。

一次运行的顺序

下面是一次「运行一条命令、回答结果」的运行。流里每行一个事件，缩进只为阅读。

session agent_start turn_start message_start role system（系统提示与工具定义） message_end role system message_start role user（提示词） message_end role user 第 1 次模型调用：thinking 之后一个 bash 工具调用 message_start role assistant，content []，stopReason pending message_update ×N thinking_start、thinking_delta…、toolcall_start、toolcall_delta… message_update thinking_end（usage 从这里开始非零） message_update toolcall_end message_end role assistant，stopReason toolUse tool_execution_start bash tool_execution_update partialResult.content [] tool_execution_update partialResult.content 含输出 tool_execution_end result，isError false message_start role toolResult message_end role toolResult turn_end message 为 assistant 消息，toolResults 含 1 项 第 2 次模型调用：文字回答 turn_start message_start role assistant message_update ×N thinking_*、text_start、text_delta…、text_end message_end role assistant，stopReason stop turn_end toolResults [] agent_end messages 含以上全部消息，willRetry false agent_settled

要点：

  • system 与 user 消息的 message_start 与 message_end 内容相同，紧挨着出现。system 消息只在第一次 turn_start 之后出现一次。
  • 一次模型调用返回多个工具调用时，所有 tool_execution_start 先出现，然后是各自的 tool_execution_update 与 tool_execution_end，再是每个工具一对 toolResult 的 message_start 与 message_end。样本中两个工具调用的 tool_execution_start 连续出现，说明工具是并行执行的。用 toolCallId 关联。
  • turn_end.message 与前一个 assistant 消息的 message_end.message 相同；turn_end.toolResults 与这一轮各 toolResult 消息相同。agent_end.messages 包含本次运行产生的所有消息，从 system 消息开始。因此这些字段里的内容在流里会重复出现三次，只需在一处解析。
  • agent_settled 是正常运行的最后一行。文档说明 agent_end 之后可能还有自动重试、溢出恢复、压缩重试，这时会再次出现 agent_start，直到 agent_settled。

message 事件

message_start 与 message_end 只有一个字段 message。message.role 决定对象的其余字段。观测到四种角色：system、user、assistant、toolResult。文档另外定义了 bashExecution（RPC 的直接 shell 命令）、custom（扩展注入的上下文）、branchSummary 与 compactionSummary（压缩产生的摘要），解析器应容忍未知角色。

system 消息

第一次 turn_start 之后出现一次，声明系统提示与工具定义。message_start 与 message_end 的内容相同。

字段类型含义备注
rolestringsystem观测
contentstring 或 array观测值为空字符串 ""，正文在 sections 里。文档允许 TextContent[]观测
sectionsobject键为节名，值为字符串或 null。观测到 preamble、tools、rules、docs、cwd 五节。按顺序拼接得到系统提示观测

toolsRemovedarray后续 system 消息移除的工具引用文档；可能缺失
replacebooleantrue 表示丢弃之前的 system 状态，以这条消息为新的基线文档；可能缺失
timestampnumberUnix 毫秒观测

assistant 消息

message_start 里的 assistant 消息是空壳：content 为 []，usage 全为 0，stopReason 为 pending，没有 responseId 与 rawStopReason。message_end、turn_end.message 与 agent_end.messages 里是完整消息。

providerstringprovider 名，观测值 deepseek观测
modelstring请求的模型 id，观测值 deepseek-flash观测

diagnosticsarrayprovider 或运行时诊断文档；可能缺失

stopReasonstringpending（流式输出中）、stop（文字回答结束）、toolUse（要求调用工具）、error（模型调用失败）。文档另有 length、aborted、deferred观测前四种

message_update

只在 assistant 消息流式输出时出现，有两个字段。

字段类型含义备注

usage 对象

出现在 assistant 消息的 usage 与 message_update.usage，都是单次模型调用的量，流里没有整次运行的累计值，需要读取方把每个 assistant message_end 的 usage 相加。

字段类型含义备注
inputnumber未命中缓存的输入 token。观测中 input + cacheRead + output = totalTokens，所以 input 不含 cacheRead观测
outputnumber输出 token，已包含 reasoning观测
cacheReadnumber命中缓存的输入 token观测
cacheWritenumber写入缓存的 token，deepseek 观测值为 0观测
cacheWrite1hnumbercacheWrite 中按一小时保留写入的部分文档；可能缺失
reasoningnumber推理 token，是 output 的子集，不要重复相加观测；pending 状态与错误消息的 usage 里没有；0.73.1 没有
totalTokensnumber总 token观测
costobject{input, output, cacheRead, cacheWrite, total}，单位美元，按 pi 模型目录里的单价计算观测

文档中有、样本中没有的事件

auto_retry_start、auto_retry_end

模型调用失败后，pi 按 delayMs 延迟后重新开始一次 agent 运行。0.73.1 的样本（网络不通，errorMessage 为 Connection error.）显示了完整的重试序列：首次失败的 agent_end 之后，auto_retry_start（attempt 1、2、3，maxAttempts 3，delayMs 2000、4000、8000）各自后跟一整组 agent_start 到 agent_end，最后 auto_retry_end 带 success: false 与 finalError。重试的 agent 运行里没有 user 消息。1.0.1 的样本中 401 认证错误没有触发重试，直接结束运行，说明重试只针对部分错误类型。

type字段类型含义
auto_retry_startattemptnumber第几次重试，从 1 开始
maxAttemptsnumber最多重试次数
delayMsnumber重试前的等待毫秒数
errorMessagestring触发重试的错误
auto_retry_endsuccessboolean重试是否成功
attemptnumber结束时的尝试序号
finalErrorstringsuccess 为 false 时的最终错误

{"type":"auto_retry_end","success":false,"attempt":3,"finalError":"Connection error."}

compaction_start、compaction_end

上下文接近上限时 pi 自动压缩历史。compaction_start 有 reason，取值 manual、threshold、overflow。compaction_end 有 reason、aborted、willRetry，成功时有 result（{summary, firstKeptEntryId, tokensBefore, estimatedTokensAfter, usage, details}），失败时没有 result 而有 errorMessage。溢出恢复成功后 willRetry 为 true，pi 会重新发送提示词。压缩失败的重试用 summarization_retry_scheduled（attempt、maxAttempts、delayMs、errorMessage）、summarization_retry_attempt_start（source 为 compaction 或 branchSummary，reason 同上）与 summarization_retry_finished 表示。压缩完成后的历史里会出现 compactionSummary 角色的消息。

队列与状态事件

queue_update（steering、followUp，各为完整的当前队列）、entry_appended（entry，会话文件的条目对象）、session_info_changed（name，缺失表示清除）、thinking_level_changed（level）。它们由交互操作或扩展触发，在没有扩展的 JSON 模式一次运行里不会出现。
