claude-code

参数

<claude 的绝对路径> -p --output-format stream-json --verbose
  --input-format stream-json --replay-user-messages
  --permission-mode auto
  --setting-sources ""
  --strict-mcp-config
  --no-session-persistence
  --session-id <新生成的 UUID v4>
  --tools Read,Edit,Write,Glob,Grep,Bash,Task
  --allowedTools Read,Edit,Write,Glob,Grep,Task
  [--settings <沙箱设置>]
  [--model ID] [--effort LEVEL] [--max-turns N]
  <-- 之后的调用方参数>
  • --setting-sources "" 不加载用户、项目与本地设置，工作目录里的 CLAUDE.md 不进入模型上下文（实测）。因此沙箱设置只来自 --settings。
  • --strict-mcp-config 不加载任何 MCP 服务器。
  • --session-id 每次新生成，与 --no-session-persistence 一起用。理由：在 Claude Code 会话里运行 agentrun 时，claude -p 子进程会继承父会话的 id，把记录写进父会话，只加 --no-session-persistence 不能避免。
  • --tools 限定可用的内置工具，去掉网页工具与技能等。--allowedTools 放行列出的工具，不经权限判断。Bash 不在放行列表里：沙箱打开时由 autoAllowBashIfSandboxed 自动放行，沙箱没有运行时由 auto 模式逐条判断。只用 --tools 而不放行时，auto 模式会拒绝 Write，且结果仍报告成功（实测）。
  • 启动 subagent 的工具在参数与 system/init 的工具列表里叫 Task，在输出的 tool_use 里叫 Agent，两个名字都要识别。--no-subagents 从 --tools 与 --allowedTools 里去掉 Task，生效与否看 init 的工具列表里有没有 Task。
  • --network full 时两个列表都加上 WebFetch 与 WebSearch；custom 时 --tools 加 WebFetch，--allowedTools 每个主机加一条 WebFetch(domain:HOST)。
  • 提示词从标准输入传入，不在命令行里：写入一行 JSON {"type":"user","message":{"role":"user","content":"<提示词>"}}，然后关闭标准输入。--replay-user-messages 让 claude-code 把这条消息回显到输出里，agentrun 据此输出 prompt 事件。不加这两个选项时，输出里没有提示词。实测单条提示词时，关闭标准输入后进程正常结束（退出码 0）；多行或很长的提示词、不关闭标准输入、与 SIGINT 和 subagent 同时出现的情况待实测。

{
  "sandbox": {

    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "allowWrite": ["<cwd 的绝对路径>", "<会话临时目录>"]
    },
    "network": {
      "allowedDomains": []
    }

}

前三项以外的设置（failIfUnavailable、allowWrite、空的 allowedDomains）取自 claude 的设置说明，还没有实测是否生效。--network full|custom 时另加 network.httpProxyPort 与 socksProxyPort 指向过滤代理。

auto 模式没有生效时终止

claude-code 在某些模型下不支持 auto 模式，这时它不报错，而是改用 default 权限模式：system/init 的 permissionMode 为 default，Bash 命令全部被拒绝，退出码仍为 0。实测 haiku 作主模型时如此，sonnet 正常。agentrun 读到 init 的 permissionMode 不是 auto 时，立即向进程组发 SIGKILL，判为 failed，detail 写明实际的权限模式、当前模型与「换一个支持 auto 模式的模型」。理由：否则一次什么命令都没执行的运行会被报告为成功；agentrun 不替调用方选模型，默认配置可能落到任何模型上。

失败判定

以下任一成立即为 failed，detail 按顺序取第一项的信息：

  1. auto 模式没有生效（见上）。
  2. 最后一个 result 的 is_error 为 true：取它的 result 文字。例如无效模型（同时退出码 1、标准错误有 [claude-code:unrecognized_model]）、无效凭据（退出码 1）。
  3. 退出码非 0：取标准错误的最后 500 个字符。例如未知选项，没有任何事件。
  4. 退出码 0 但没有 result：运行时退出（退出码 N）时没有输出 result 事件。

收到 SIGINT 时 claude-code 约 0.4 秒退出，退出码 0，最后的 result 为 is_error: true、subtype error_during_execution；SIGTERM 时退出码 143、没有 result。两种情况都由 agentrun 记为 interrupted。

auto 模式的分类器会拒绝部分命令。实测稳定被拒绝的是读取凭据的命令，例如 cat ~/.ssh/id_rsa；用 curl 把文件外发会触发模型的安全拦截，整次运行以 API Error 失败。

pi

参数

<pi 的绝对路径> -p --mode json --no-session
  --no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files
  --no-approve --offline
  --tools read,bash,edit,write,grep,find,ls
  [--model 服务商/模型] [--thinking LEVEL]
  <-- 之后的调用方参数> -- <提示词>
  • --no-context-files 不读 AGENTS.md 与 CLAUDE.md；--no-approve 不信任工作目录里的项目级配置，因为工作目录 agent 可写，项目级配置能在 pi 进程内执行代码；--offline 启动时不联网下载资源。
  • 提示词是命令行的最后一个参数，放在 -- 之后、调用方参数之后，所以调用方的参数不会被当成提示词。标准输入启动后立即关闭。
  • --effort 传成 --thinking。--max-turns 是用法错误；--no-subagents 不起作用，也不报错。
  • 沙箱打开时，整条命令前面加上包裹命令，见隔离：Linux 是 bwrap --ro-bind / / --bind <cwd> --bind <临时目录> --bind <状态目录> --dev /dev --proc /proc --die-with-parent --unshare-net -- ...，macOS 是 /usr/bin/sandbox-exec -f <临时目录>/seatbelt.sb ...。状态目录在 cwd 之下时不再单独绑定。

模型检查

--model 必须写成 服务商/模型，可以带 :推理强度 后缀；没有 / 或任一侧为空时是用法错误。理由：pi 对模型名做模糊匹配，能匹配上的未知模型名会被换成别的服务商的模型，退出码仍为 0。例如环境里有 AWS_ 变量时，deepseek/deepseek-v4-flash（1.0.1 已改名为 deepseek-flash）被换成了 Amazon Bedrock 上的模型。

给了 --model 时，agentrun 在第一个 assistant 的 message_start（此时还没有请求模型）比较它的 provider 与 model，区分大小写，不做别名处理。不一致时向进程组发 SIGKILL，判为 failed，detail 为 pi 实际使用 <provider>/<model>，与 --model <值> 不符。

没给 --model 时不传，pi 用它 settings.json 里的默认模型。设置里的模型不存在、或者没有设置文件时，pi 同样会不提示地改用环境里其他可用的服务商。这种情况由 doctor 的登录检查发现：它报告 pi 实际选中的服务商与模型，与设置不一致时失败。

输出映射

--mode json 每行一个事件，只用以下三种，其余（session、message_update、turn_end、agent_end 等）只写入 --raw。不用 turn_end 与 agent_end，因为它们重复 message_end 的内容，会重复计算用量。

原始事件转成
tool_execution_endtool：id 为 toolCallId，name 为 toolName，parent 为 null，denied 为 false（isError 表示执行出错，不是拒绝）。args 不在这个事件里，从对应的 tool_execution_start 取。同一条消息里的多个调用并行执行，结束顺序可能与开始顺序不同
assistant 的 message_endtext：全部 text 元素按顺序用换行连接，不输出 thinking；之后输出 usage：model 为 provider/model，input、output、cacheRead、cacheWrite 对应四个字段（input 不含缓存命中，实测）；reasoning 与 cost 不进统一事件
user 的 message_endprompt：全部 text 元素按顺序用换行连接
第一个 assistant 的 message_start不输出；用于模型检查

summary：bash 写 command 的第一行；read、write、edit、ls 写 path（ls 没有 path 时写 .）；grep、find 写 pattern；其他只写工具名。end.result 是最后一个 text。

失败判定

以下任一成立即为 failed，detail 按顺序取第一项的信息：

  1. 模型检查不通过。
  2. 退出码非 0：取标准错误的最后 500 个字符。
  3. 最后一条 assistant 消息的 stopReason 为 error 或 aborted：取 errorMessage 的前 500 个字符，没有时写 stopReason: 值。
  4. 退出码 0 但没有 assistant 的 message_end：pi 没有输出模型回复。
