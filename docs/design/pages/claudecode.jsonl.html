claude-code 事件流 字段参考

本文是 claude -p --output-format stream-json --verbose 输出的事件流的字段参考：每种事件何时出现、有哪些字段、字段的类型与含义、典型运行的顺序、subagent 的嵌套方式、错误与退出码。写给要为这条流写解析器的人，不依赖 agentrun 的其他文档。依据是 claude-code 2.1.288 与 2.1.289 在 Linux 容器里的实测输出，字段表中标出了每一项的来源。

读这条流的三条规则：每行一个 JSON 对象，按 type 与 subtype 分发，不认识的类型跳过；一次运行可能有多个 result 事件，以最后一个为准；成败看最后一个 result 的 is_error，退出码只区分启动失败与运行时的限额失败。

怎样产生这条流

claude -p "提示词" \
  --output-format stream-json --verbose \
  --model sonnet --session-id "$(uuidgen)" --no-session-persistence \
  --permission-mode auto --setting-sources "" --strict-mcp-config

-p（--print）让 claude 处理一个提示词后退出；--output-format stream-json 选择逐行 JSON 输出；--verbose 是必需的，缺少它时进程不输出任何事件，在标准错误打印 Error: When using --print, --output-format=stream-json requires --verbose，退出码 1。提示词也可以从标准输入传入。

事件流写到标准输出，标准输出里只有 JSON 行。诊断信息写到标准错误，例如模型名不存在时的 [claude-code:unrecognized_model] {"model":"...","query_source":"sdk"}。

以下选项与环境变量改变流里出现的事件：

选项对流的影响
--include-partial-messages
环境变量 CLAUDE_CODE_INCLUDE_PARTIAL_MESSAGES=true		加入 stream_event 事件，每个模型调用的逐字输出都会出现。见「stream_event 事件」。本文的部分样本来自设置了该环境变量的环境，显式选项的效果以帮助文本为依据

每行的格式

每行是一个 JSON 对象，以 LF 结尾，没有空行，没有非 JSON 行。每个对象都有 type；type 为 system 与 result 的对象还有 subtype。下面的字段出现在多种事件上：

字段类型含义出现在
typestring事件类型所有事件
subtypestring子类型system、result
uuidstring这一行的唯一编号除 system/api_retry 以外的所有观测到的事件都有
session_idstring会话 id，等于 --session-id 给出的值。subagent 的事件与主 agent 相同所有事件
parent_tool_use_idstring 或 null主 agent 的事件为 null；subagent 内部的事件是启动它的那次 Agent 工具调用的 id。见「subagent 与后台任务」assistant、user、stream_event
timestampstringISO 8601，UTC，毫秒。只有 assistant 与 user 事件带时间戳，其他事件没有assistant、user

字符串里可能有换行（\n）与 Unicode 行分隔符，按 LF 切行后再解析 JSON，不能按通用的行分隔符切行。

有哪些事件

「来源」一列：「观测」表示在样本中出现过；「帮助文本」表示只在 claude --help 中有描述。

一次运行的顺序

下面是一次「写文件、读回、回答」的运行，没有开启逐字输出。缩进只为阅读，流里每行一个事件。

启动 active_goal autocompact_state rate_limit_event system/init 第 1 次模型调用：一个 Write 工具调用 system/status assistant content: tool_use Write system/task_summary user content: tool_result 第 2 次模型调用：thinking 之后一个 Read 工具调用 system/status assistant content: thinking assistant content: tool_use Read user content: tool_result 第 3 次模型调用：文字回答 system/status assistant content: text system/post_turn_summary result subtype success, num_turns 3 system/task_summary

要点：

  • 一次模型调用返回几个内容块，就有几个 assistant 事件，它们的 message.id 相同。每个事件的 message.content 只含当前这一个块。
  • 每个工具调用对应一个 user 事件，message.content[0].tool_use_id 对应 assistant 事件里 tool_use 块的 id。一次调用里有多个工具调用时，user 事件按完成顺序出现，可能与调用顺序不同。
  • result 之后还可能有 system/task_summary，所以 result 不一定是最后一行。
  • 后台任务（后台 Bash 命令、Workflow）完成时，进程继续运行，再输出一次 system/init、新一轮的 assistant 与一个新的 result。两个 result 用 result_index（0、1）区分，第二个带 origin。进程在所有后台任务结束后退出。

开启逐字输出后，每次模型调用周围多出 stream_event，assistant 事件出现在对应内容块的 content_block_stop 之前：

system/status stream_event message_start stream_event content_block_start index 0, tool_use stream_event content_block_delta ×N input_json_delta assistant content: tool_use（完整参数） stream_event content_block_stop index 0 stream_event message_delta stop_reason, usage stream_event message_stop system/task_summary user tool_result

文字类的 user 消息

message.content[0].type 为 text 的 user 事件有三种：subagent 收到的提示词（带 parent_tool_use_id，文字等于 Agent 调用的 prompt）；SIGINT 中断时的 [Request interrupted by user]；isSynthetic: true 的注入内容。这些事件没有 tool_use_result。

subagent 与后台任务

主 agent 用名为 Agent 的工具启动 subagent（system/init 的 tools 列表里这个工具叫 Task，--tools 与 --disallowedTools 也用 Task 这个名字）。一次 subagent 的完整事件序列：

assistant tool_use Agent，id 为 toolu_P，input: {description, prompt, subagent_type, run_in_background} system/task_started task_id, tool_use_id: toolu_P user parent_tool_use_id: toolu_P，content: text（subagent 收到的 prompt） system/task_progress usage: {total_tokens, tool_uses, duration_ms} assistant parent_tool_use_id: toolu_P，subagent 的工具调用 user parent_tool_use_id: toolu_P，subagent 的工具结果 assistant parent_tool_use_id: toolu_P，tool_use SubagentHandback（subagent 交回报告） user parent_tool_use_id: toolu_P，SubagentHandback 的结果 system/task_updated patch: {status: "completed", end_time} system/task_notification status: "completed"，usage user parent_tool_use_id: null，content[0].tool_use_id: toolu_P，主 agent 收到的 Agent 工具结果

要点：

  • subagent 内部的 assistant 与 user 事件都带 parent_tool_use_id，值等于 Agent 调用的 tool_use id；还带 subagent_type 与 task_description。主 agent 的事件 parent_tool_use_id 为 null。
  • 多个 subagent 并行时，它们的事件与主 agent 的事件交错出现，用 parent_tool_use_id 归属。subagent 再启动 subagent 时嵌套规则相同，task_started.spawn_depth 给出深度。观测到的最大深度为 1。
  • subagent 内部的 assistant.message.usage 是它自己每次模型调用的用量；result.usage 不包含它们，result.modelUsage 包含。
  • subagent 的模型调用没有产生 stream_event，也没有 system/status。
  • subagent 最后通过 SubagentHandback 工具交回报告，报告正文在主 agent 收到的工具结果的 tool_use_result.handbackReport.text 里。

后台 Bash 命令与 Workflow

Bash 工具带 run_in_background: true 时，工具结果立即返回，tool_use_result.backgroundTaskId 给出任务 id，随后出现 background_tasks_changed、task_started（task_type: local_bash，is_backgrounded: true）。命令结束后出现 task_notification（没有 usage）、background_tasks_changed、task_updated，然后 claude-code 开始新一轮：再输出 system/init，模型处理通知，输出新的 result。

Workflow 工具（task_type: local_workflow）按脚本启动多个 subagent。它的内部 agent 不产生带 parent_tool_use_id 的 assistant 与 user 事件，进度只在 task_progress.workflow_progress 里。

版本与环境说明

  • 样本来自 claude-code 2.1.288 与 2.1.289，两者的事件类型与字段集没有发现差异。
  • active_goal、autocompact_state、rate_limit_event 三种事件只在 Claude 云端容器里观测到。autocompact_state.value.source 为 env，说明它来自环境变量配置；rate_limit_event.rate_limit_info 含 status、resetsAt、rateLimitType、overageStatus、overageDisabledReason、isUsingOverage、unifiedWindows.{five_hour, seven_day}.{utilization, resetsAt}，描述订阅的用量窗口；active_goal.value 观测值为 null。其他环境里是否出现未验证，解析器应把它们当作可选事件。
  • system/init 的 tools、skills、slash_commands、plugins 列表和 startup_timing、result 的计时字段随环境与版本变化，本文只列出键名，不保证完整。
  • thinking 块的正文在样本里都是空字符串，只有签名与 token 估计；这可能是账号或模型的设置，解析器不应假设 thinking 正文可读。
  • 未实测的选项：--forward-subagent-text、--input-format stream-json、--replay-user-messages、--fallback-model、MCP 工具（mcp__ 前缀的工具名）与上下文压缩（compact）过程中的事件。
