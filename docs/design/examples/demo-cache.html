linecount 增量统计缓存 示例

linecount 第二次在同一个目录运行时，只重新统计改动过的文件，其余文件的行数从缓存读取。本文档写缓存的数据流、判断文件是否变化的规则、缓存文件的位置和格式，以及并发与正确性的保证。命令和配置见 命令与配置。

缓存只用来加速。

使用缓存和不使用缓存的统计结果必须完全一致，任何无法确定文件是否变化的情况都重新统计。

第二次运行时发生了什么

scanner 产生的每个路径先查缓存：命中的文件直接使用缓存里的行数，未命中的文件交给 counter 重新统计。两部分合并成 Summary 后交给 reporter，同时把本次见到的所有文件写回缓存。

模块输入输出接口
cache统计根目录上次运行保存的缓存；文件不存在或无法解析时返回空缓存load(root: Path) -> Cache
cache缓存、文件路径和它的 stat 结果命中时返回缓存条目，否则返回 Nonelookup(cache: Cache, path: Path, st: os.stat_result) -> CacheEntry | None
cache统计根目录、本次见到的所有条目写入缓存文件save(root: Path, entries: dict[str, CacheEntry]) -> None
counter未命中的文件路径Summary；读取失败的文件记入 skippedcount(paths: Iterable[Path]) -> Summary
 
@dataclass
class CacheEntry:
    path: str
    size: int
    mtime_ns: int
    lines: int

@dataclass
class Cache:
    version: int
    written_at_ns: int
    entries: dict[str, CacheEntry]

@dataclass
class Summary:
    by_ext: dict[str, ExtStat]
    skipped: list[Path]

@dataclass
class ExtStat:
    files: int
    lines: int

高亮的 size 和 mtime_ns 是判断文件是否变化的依据，见下一节。CacheEntry.path 是相对统计根目录的路径，Cache.entries 以它为键。命中的文件按扩展名直接累加进 Summary.by_ext，与 counter 统计出的结果合并；合并后的 Summary 与不使用缓存时的结构完全相同，reporter 的代码不涉及缓存。

怎样判断文件没有变化

lookup 用三个条件判断，全部满足才算命中：

  1. 缓存里有同一个相对路径的条目。
  2. 文件大小与条目的 size 相同。
  3. 文件的 mtime_ns 与条目相同，并且早于上次写缓存的时间 Cache.written_at_ns。

不计算内容哈希。理由：计算哈希要读完整个文件，统计行数也只需要读一遍文件，用哈希判断文件是否变化不比直接重新统计更快。

git checkout 会改变被切换文件的 mtime，导致这些文件重新统计，这是可以接受的代价。

mtime 精度问题：文件系统的时间戳精度有限，一个文件如果在上次写缓存后、时间戳精度以内的时间里被修改，mtime 可能与缓存记录的相同。修改时间不早于上次写缓存时间的文件一律视为已变化，与 git 处理同类问题的方式相同。

缓存放在哪里

缓存文件放在用户缓存目录下的 linecount/ 子目录（Linux 和 macOS 上是 $XDG_CACHE_HOME/linecount/，默认 ~/.cache/linecount/），文件名是统计根目录绝对路径的 SHA-256 前 16 个十六进制字符加 .json。不放在被统计的仓库里。理由：放在仓库里会让 git status 多出一个未跟踪的文件，也容易被误提交。

选项 --no-cache 跳过缓存的读和写，列在 命令与配置 的选项表中。

两个进程同时运行会怎样

两个 linecount 进程同时统计同一个目录时，各自读到同一份旧缓存，各自统计，最后各自写缓存。写入时先写到同目录下的临时文件，再原子重命名为正式文件名，后写入的覆盖先写入的，不加锁。理由：lookup 会用 size 和 mtime 逐条校验缓存条目，所以无论保留哪个进程写的缓存，统计结果都正确；加锁只会让第二个进程等待，而丢失一个进程的缓存只会让下次多统计几个文件。原子重命名保证读取方不会读到写了一半的文件。

缓存文件的格式、版本和大小

{
  "version": 1,
  "written_at_ns": 1790000000000000000,
  "entries": {
    "src/main.py": {"size": 4821, "mtime_ns": 1789990000000000000, "lines": 212},
    "src/util.ts": {"size": 913, "mtime_ns": 1789980000000000000, "lines": 48}
  }
}

常量 CACHE_VERSION = 1 写在文件的 version 字段。读取时版本不一致、文件无法解析，都丢弃整个缓存，当作第一次运行。理由：格式变化时逐条迁移的代码没有收益，重新统计一次就能得到新格式的缓存。

保存时只保留本次运行见到的文件，被删除或被排除的文件的条目不再写入，所以缓存不会随历史积累增长。另外设上限 MAX_CACHE_BYTES = 50_000_000，序列化后超过这个大小的缓存不写入，并丢弃已有的缓存文件。

怎样确认缓存正确

测试里对同一个目录连续运行三次：第一次不带缓存，第二次使用缓存，第三次加 --no-cache。三次的 Summary 必须完全一致。在第二次和第三次之间修改一个文件、新增一个文件、删除一个文件，再比较使用缓存和 --no-cache 的结果，同样要求一致。测试使用临时目录和临时的缓存目录，不读写用户的缓存目录。
